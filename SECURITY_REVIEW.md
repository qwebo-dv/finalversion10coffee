# Проверка безопасности — 5 сентября 2026

Проверен локальный checkout `shop` проекта `qwebo-dv/finalversion10coffee`. Изменения не опубликованы. Это целевая проверка наиболее опасных путей доступа, а не полный пентест.

## Исправления

| Проблема в исходном коде | Исправление и источник |
| --- | --- |
| `getOrderById` и `getAllOrders` читали заказы без проверки доступа. | Чтение отдельного заказа ограничено клиентом текущей сессии; общий список требует сессии администратора Payload и выполняется с `overrideAccess: false`. `lib/actions/orders.ts`, `lib/auth/payload-admin.ts`. |
| `updateOrderStatus` проверял только наличие клиентской сессии, позволяя запросить изменение чужого заказа. | Требуется административная роль управления заказами; чтение и изменение дополнительно проходят ACL Payload, включая ограничения опта/розницы. `lib/actions/orders.ts`. |
| Шесть серверных функций МойСклад и отправка промокода не проверяли права вызывающего. | Проверка сессии Payload и соответствующей роли перед интеграцией или отправкой письма. `lib/actions/moysklad.ts`, `lib/actions/orders.ts`. |
| Заказы искались по совпадению email либо имени и телефона, которые пользователь мог менять. | Владение определяется связью заказа с клиентом, найденным по ID сессии. Удалены также автоматические совпадения по email при синхронизации профиля и розничном checkout. `lib/actions/orders.ts`, `lib/actions/shop-orders.ts`, `app/api/auth/me/route.ts`, `app/api/auth/social/callback/route.ts`. |
| API профиля принимал произвольные метаданные, в том числе `user_type`, `customer_type`, `email_verified`. | Разрешены только пять полей профиля с проверкой типа и размера. Смена email заблокирована до появления подтверждения нового адреса. `lib/auth/profile-input.ts`, `app/api/auth/me/route.ts`. |
| Вход через соцсеть автоматически связывал существующий аккаунт по email. | Для существующего аккаунта требуется вход по паролю и явная привязка в настройках; уже сохранённые связи по ID провайдера остаются рабочим путём. `app/api/auth/social/callback/route.ts`. |
| Создание и изменение компании передавало входные поля непосредственно в SQL-адаптер. | Схемы Zod отбрасывают `id`, `client_id`, `moysklad_counterparty_id` и другие служебные поля; владельца при создании задаёт сервер. `lib/company-input.ts`, `lib/actions/companies.ts`. |
| Клиент мог физически удалить собственный заказ независимо от оплаты и исполнения. | Физическое удаление заменено отменой нового неоплаченного заказа с дополнительными фильтрами владельца и состояния при обновлении. `lib/actions/orders.ts`, `components/dashboard/orders-list.tsx`. |
| ACL собственной записи администратора не проверял auth-коллекцию; `unlock` явно не ограничивался. | Обязательна коллекция `admins`; разблокировка разрешена только `admin`/`super_admin`. `payload/collections/Admins.ts`. |

Эти выводы основаны на исходном коде и тестах с подменёнными внешними адаптерами. Сборка включила `getAllOrders`, `getOrderById`, `updateOrderStatus`, `sendPromoCodeEmail` в `.next/server/server-reference-manifest.json` как Server Actions; отсутствие кнопки в интерфейсе не является проверкой доступа.

## Проверки и ограничения

- `node --test scripts/test-security.cjs`: 15 тестов, все прошли. Проверяются гостевой доступ, чужие заказы, роли, фильтры ACL, служебные поля, компания, сохранность оплаченного заказа и отказ от автоматической OAuth-привязки по email.
- `node node_modules/typescript/bin/tsc --noEmit --incremental false`: прошёл. Проверка запускалась отдельно, поскольку конфигурация Next.js уже содержит `ignoreBuildErrors: true`.
- `node --max-old-space-size=4096 node_modules/next/dist/bin/next build`: производственная сборка прошла.
- ESLint изменённых серверных модулей, теста и списка заказов: без ошибок; в списке заказов остаётся предупреждение о существующем `window.location.assign`.
- Страница настроек имеет существующую ошибку `react-hooks/set-state-in-effect` на строке 70 и два предупреждения. Они воспроизведены на `git show HEAD:app/dashboard/settings/page.tsx` с обновлённым линтером; полный проект не объявляется lint-clean.
- Локальные проверки выполнены на Node.js `24.20.0`; проект и Dockerfile требуют ветку Node.js 22. Проверка именно на Node.js 22 и в production-контейнере не выполнена.
- Проверка отслеживаемых Git файлов по сигнатурам приватных ключей, GitHub/AWS/Stripe-токенов совпадений не выявила. Это не проверка всей истории Git и не гарантия отсутствия других секретов.
- Реальные оплаты, SMTP, OAuth, миграции, серверные настройки и production-доступ не тестировались. Запросы тестов не обращаются к рабочей БД и не отправляют письма.

## Изменения пользовательских сценариев

Гостевые и исторические заказы без связи с клиентом больше не появляются в кабинете только по совпадению контактов. Их безопасная привязка требует отдельного подтверждения владения. Смена email аккаунта пока недоступна; для заказа контактный email задаётся при оформлении. Социальную сеть для существующего email-аккаунта необходимо привязать после входа. Вместо удаления заказа доступна отмена нового неоплаченного заказа.

Следующие отдельные задачи по найденному коду: подтверждаемый токеном сброс пароля вместо немедленной смены в `lib/actions/auth.ts:resetPassword`, ограничение частоты попыток локального входа в `lib/auth/local.ts:verifyPassword`, проверка сертификата удалённой БД вместо `rejectUnauthorized: false` в `lib/db.ts`. Они не включены в выполненные исправления.
